# Durable ingestion jobs, controlled retry and safe reprocessing (V41-12.03, V41-12.04)

Added in Batch 9 (migration `0010`) and completed in Batch 10 (migration `0011`: retained original content). Both requirements are **implemented and tested but not marked Verified**: owner review decides. Implementation: `backend/app/ingestion/jobs.py`, worker integration in `backend/app/workflows/worker.py`, routes in `backend/app/api/v1/domain_routes.py`. Design written before implementation: [batch9-manifest.md](../planning/batch9-manifest.md).

## Why a job table
Before Batch 9 a failed upload left no record and relied on the client repeating it. The `ingestion_jobs` table is now the durable record and the queue: it holds per-job state (attempts, schedule, lease, sanitised error, outcome) that an outbox row cannot. The existing worker loop drains it (`process_one` runs ticket submissions, then document cleanups, then ingestion jobs) with the same claim pattern, lease and backoff helper.

## State machine (server controlled; no client or model can set a state)
`QUEUED -> PROCESSING | CANCELLED`; `RETRY_PENDING -> PROCESSING | CANCELLED`; `PROCESSING -> COMPLETED | RETRY_PENDING | FAILED | CANCELLED`; `FAILED -> QUEUED` (authorised manual retry, reprocess jobs only); `COMPLETED` and `CANCELLED` are final. Every change goes through one function that rejects anything else; database CHECK constraints independently enforce: terminal state iff `completed_at`, `PROCESSING` iff a lease, attempts within `max_attempts` (at most 5 by default, never more than the column bound), and content payload present only while the job can still run.

## Claims, leases and fencing
A claim takes the row `FOR UPDATE SKIP LOCKED`, sets `claim_token` and `locked_until` (60 s). Every later write (retry, failure, completion, the data write itself) re-locks the job row and refuses unless the token still matches and the job is `PROCESSING`. A worker that lost its lease (crash, stall) therefore cannot write; the expired lease is reclaimed, the lost attempt counts, so retries stay bounded.

## Retry
Transient failures (embedding model unavailable, database connectivity, timeouts, unexpected errors) go to `RETRY_PENDING` with exponential backoff (base 2 s, cap 300 s, the shared `connectors.http.backoff_delay`) until `max_attempts`, then `FAILED`. Permanent failures (validation, unsupported or changed source) fail at once. Stored errors are fixed, sanitised messages (`error_code` plus a generic detail): never document text, exception text, stack traces or secrets.

## Retained original content (Batch 10, migration 0011)
The original bytes of every upload are kept in the PostgreSQL table `document_sources` (not on a filesystem): they commit in the same transaction as the job, are covered by the existing backups, sit under the same row-level security as all tenant data, and are removed by the existing deletion cleanup. No path exists anywhere to forge, and no API route returns the bytes; only tenant-scoped server code (the upload path and the worker) reads them. Content is immutable (the application and worker roles have no UPDATE on bytes, hash or size), bounded (the 10 MiB upload limit, plus a database CHECK at 16 MiB), and its SHA-256 is re-verified on every read (`source_corrupted` if it differs). Parse options (CSV field map, id field) are stored with it so the same parser configuration is re-applied. Documents uploaded before 0011 have no retained original and remain fully supported, except that they cannot be reprocessed from source (below).

Lifecycle of a source: stored with the job; linked to the document version created from it, in the same transaction as the document, chunks and job completion; deleted when its job is cancelled, ends in a permanent failure, or resolves to a duplicate; kept (unlinked) when retries are exhausted so the job can be re-queued; deleted with the document, all versions, by the cleanup, which verifies none remain.

## Upload (contract unchanged)
`POST /documents` stays synchronous with the same responses. Order: duplicate check, parse (a permanent failure is recorded as a `FAILED` job, stores no content, and returns the same error), job opened **and the original stored** in one transaction, claimed inline, embed, then document, version, chunks, source link and job completion commit in **one** transaction. On a transient failure the job is saved `RETRY_PENDING` and the response is the same `503 embedding_unavailable` with `Retry-After`: success is never reported before indexing completed, and a repeated identical upload while the first is unresolved is also a 503, never a fabricated duplicate. The worker later re-reads the original, re-parses and finishes the job (or the client's repeat upload resumes it). Jobs no longer keep parsed text in `payload` (only jobs created before 0011 do). Idempotency: one active job per `(tenant, ingest:<sha256>)`; a repeat while another request holds the job waits (up to 15 s) for that request and resolves to its result, exactly like a sequential repeat (`201 duplicate`, the pre-Batch-9 contract, kept by fault-injection test FI-09 and the Batch 10 concurrency test: six simultaneous identical uploads give one document and one retained original); only if the other request is still busy after the wait does it answer `503 ingestion_in_progress`.

A job that exhausted its retries (`FAILED retries_exhausted`) keeps its original, and `POST /ingestion/jobs/{id}/retry` (administrator or supervisor) re-queues it without the client uploading again. A permanently failed job (invalid content, missing or corrupted original) keeps nothing and cannot be retried.

## Reprocessing (genuine source reprocessing, Batch 10)
`POST /documents/{id}/reprocess` (tenant administrator or supervisor; `202`) queues a `reprocess` job (key `reprocess:<document id>`). The worker (1) reads the original retained for the current version and verifies its checksum against the stored hash and the version, (2) re-runs the supported parser with the stored options, (3) generates new text and chunks, (4) embeds them, (5) stages them as a **new generation** that retrieval cannot see, (6) validates counts and vectors, and (7) in one transaction with the job completion makes it current and retires the previous generation (`document_versions.active_generation`, `chunk_count`, `processing_job_id`). Any failure rolls back and the previous generation keeps serving. It does not read the old chunks (a test tampers with them and shows the new generation comes from the file). Retired generations stay (non-current) so historical citations keep their meaning; they are removed with the document.

**Documented limitation:** a document without a retained original (uploaded before 0011) is refused at request time with `409 source_not_retained` and an explicit message; upload the file again to enable reprocessing. Chunk re-embedding for such documents remains available as the separate reindex tool (`scripts/reindex_embeddings.py`) and is not presented as reprocessing. A missing or corrupted original fails the job permanently (`source_missing`, `source_corrupted`) and leaves the active generation untouched.

## Deletion interaction (Batch 8 guarantees intact)
Deleting a document cancels its active jobs (`CANCELLED`, `document_deleted`, counted in the audit event) and releases the unlinked originals of those jobs at once. Every final write (store, activation) re-locks the document row and refuses a non-active document, so a job can never revive or add content to a deleted document. Cleanup removes all generations and every retained original (the audit event records `sources_removed`, no content), verifies none remain, and touches only the document's own tenant and rows: a replacement upload of the same bytes has its own source and is unaffected.

## API (typed, tenant scoped, closed response models)
`GET /ingestion/jobs` (page; filters `status`, `job_type`, `document_id`), `GET /ingestion/jobs/{job_id}`, `POST /documents/{document_id}/reprocess`, `POST /ingestion/jobs/{job_id}/retry`. Another tenant's id is `404`, indistinguishable from unknown. The OpenAPI document now has 50 operations.

## Isolation
The application role sees jobs only through the tenant policy. The worker claims across tenants (like the outbox) but every content write runs in a tenant-scoped session (`worker_tenant_scoped` policies on documents, versions, chunks, embedding profiles); no RLS bypass, no superuser. Worker column privileges are limited (it cannot edit chunk text, document lifecycle status or content hashes).

The failure exercised live is a **simulated** embedding failure (a fault switch in `scripts/fault_boot.py` makes the embedder raise; same failure mode as an unloadable model); it is not a real infrastructure outage. Two earlier attempts of that checkpoint failed on a case-sensitive header comparison in the checkpoint script itself (kept: `20261113-041404-1c87`, `20261113-041453-2ded`); a third passed, and the fourth added the report section and the fifth (`20261113-043441-bf25`, the evidence cited) re-ran it after a fix to concurrent duplicate uploads (see above).

Not covered: no dead-letter UI; no scheduled purge of old job rows or of originals kept for jobs that exhausted their retries (they stay until the job is retried, the document is deleted, or an operator removes them); old generations use storage until deletion; the unexplained Batch 7 API-readiness stall (REL-01) remains open and was not investigated here; exposure items in [document-lifecycle.md](document-lifecycle.md) are documented, not all removed; physical erasure from PostgreSQL pages and backups is not claimed (see that register).
