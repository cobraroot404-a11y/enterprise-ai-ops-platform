# REST pull ingestion, pagination, rate limiting and live health probe (Batch 11A)

Added in Batch 11A (migration `0012`). Requirements touched: V41-12.01 (REST API records; the webhook part is Batch 11B), V41-11.01 (REST connector; CSV and webhook connectors are Batch 11B), V41-11.02 (pagination, rate limiting, live health). **None of these is marked Verified.** V41-16.04 stays Partial. Design written before implementation: [batch11a-manifest.md](../planning/batch11a-manifest.md).

## Approved interpretation
For this batch "REST API records" means: *pulling structured records from an authorised REST API and delivering them into the tenant's existing ingestion pipeline*. This is an approved implementation reading, not a declaration that V41-12.01 is satisfied. No incoming REST endpoint exists.

## Connector
A tenant connector of kind `rest` whose `config.records` object describes the source (`path`, `record_path`, `id_field`, optional `version_field`, `required_fields`, `document_kind`, `pagination`, `max_pages`, `max_records`, `max_record_bytes`, `reject_policy`, `rate`). A connector without `records` behaves exactly as before. The configuration is validated when the connector is saved (422 without echoing values) and again when a synchronisation is requested and when it runs, so a connector edited in the database cannot widen what a queued job does.

All network access uses the existing `HttpConnector`: the destination is only the stored `base_url`, checked against the server's per-tenant egress allow-list on every request with the validated address pinned, and redirects are never followed (a 302 is a permanent `source_rejected`, so a redirect-based SSRF has no effect). Paths are relative and cannot carry a scheme, authority, query, dot segments or backslash; **pagination values are tokens, never URLs** (a cursor containing `://`, `/` or whitespace is `invalid_cursor` and nothing is requested). Authentication is the existing `X-API-Key` header from `secret_ref` (an environment variable name): a connector whose secret is not set fails with `credentials_missing` before any request; headers and tokens are never logged, stored or returned (tests scan logs, errors, jobs and audit).

## Pagination (all bounded)
`cursor` (token in `next_cursor_field`, empty ends, `has_more_field` without a token is `missing_continuation`, a repeated token is `pagination_loop`), `offset` and `page` (end on an empty or short page or at `total_field`), `none` (one request). Bounds: `max_pages` (default 20, cap 100), `max_records` (default 500, cap 5000), 1 MiB per response, `max_record_bytes`, and detection of an identical repeated page. Unexpected shapes are `source_schema_invalid`. Reaching a configured bound with more data available ends the pull with outcome `synced_truncated`: it is reported, not hidden.

## Rate limiting (process-local, not distributed)
A token bucket per (tenant, connector) in the running process (`connectors/ratelimit.py`): configurable rate (0.1 to 50 requests per second) and burst (1 to 20). Waiting uses a condition with a timeout (no busy loop), every wait is bounded (30 s), a stop event ends waits at once on shutdown, and buckets are never shared across tenants or connectors. HTTP 429 and 503 `Retry-After` values (seconds, clamped to 30) pause the bucket; a page gets three bounded attempts and then fails transiently so the job retries with backoff. **This is not distributed rate limiting:** a second API or worker process has its own buckets. V41-16.04 stays Partial.

## Live health probe (opt-in)
`GET /api/v1/connectors/health?probe=true` (tenant administrator, as the existing endpoint): for each REST records connector, one bounded real request (3 s, no retry, one record requested, nothing ingested, nothing changed upstream) through the same egress and credential path. Result classes: `ok`, `connectivity`, `authentication`, `rate_limited`, `schema`, `upstream_error`, `denied`, `not_configured`; only the class, an HTTP status and a duration are kept, and the class is audited (`connector.probed`). Without `probe=true` the endpoint is unchanged and makes no network call. A configured URL or a resolvable name is never treated as health.

## Durable synchronisation (no second job framework)
`POST /api/v1/connectors/{connector_id}/sync` (administrator or supervisor, empty body) commits a `sync` job in the existing `ingestion_jobs` table and answers **202** only after that commit; a second request while one is active returns the same job. The existing worker claims it with the fenced lease (renewed before every page), pulls page by page, and processes every valid record in its own fenced transaction; the pager position and counts are saved after every page so a retry resumes where it stopped. Transient failures (network, 429/5xx, embedding model) retry with the existing bounded backoff (5 attempts); permanent failures (configuration, schema, credentials, egress, loops) fail at once; an exhausted job can be re-queued with the existing retry operation. A sync is COMPLETED only after every page was processed, with outcome `synced`, `synced_with_rejections` (invalid or conflicting records, counted) or `synced_truncated`. An invalid connector state is `409` (`invalid_connector_config`, `connector_destination_not_allowed`), other tenants' ids are `404`. Job reads (`GET /ingestion/jobs`, `?job_type=sync`) show counts and fixed error codes, never content.

## Record to document, idempotency and provenance
Each valid record becomes one document (`rest-<connector>-<record id>.json`): the record serialised canonically as a one-element JSON array, stored as a retained original and ingested by the existing JSON parser and `store_parsed`, so chunks carry the **source record id** as provenance and reprocessing from source and deletion cleanup work unchanged. Source ids are never invented: a record without a valid id is rejected (`invalid_id`).

`connector_sync_records` (one row per tenant, connector and source record id) stores the content SHA-256, the optional version marker, the document and version, the last job and a status. A repeat synchronisation compares the hash: **unchanged** is skipped (and not embedded again), **changed** becomes a new version of the same document, **new** is created. A record repeated inside one synchronisation with identical content is counted `duplicate_in_sync`; with different content the first is kept and the other is counted `conflict` (reported as `synced_with_rejections`). Because the record id is part of the stored content, two different ids never collide on content.

## Deletion and stale jobs
Deleting a synchronised document marks its sync record `deleted` (a **tombstone** that keeps the source record identity) in the same transaction. Every later synchronisation **skips** that record, whether the source record is unchanged (`skipped_deleted`) or changed (`tombstoned_changed`): a customer's deletion is an explicit decision, and a changed content hash alone is not authorisation to recreate deleted content (the changed content is not even stored). Policy decision for the owner: if automatic re-import of a changed record after deletion were ever required, it needs an explicit restore action; none exists, and none is required by the specification text. A deletion that commits between a sync's check and its write is honoured: the per-record write re-locks the sync record and the document and refuses a deleted one. A stale or concurrent claim cannot write (every write is fenced by the claim token), and cleanup removes the originals of synchronised documents like any other.

## HTTP semantics of the sync operation
`POST /connectors/{id}/sync` takes no body, so a malformed-request 400 or 422 cannot arise from it; authentication and role failures are 401 and 403; an unknown or other tenant's connector is 404. A stored connector whose configuration is invalid, or whose destination the server's egress policy does not approve for the tenant, is a **conflict between the request and the current state of the target resource** (RFC 9110 section 15.5.10), hence 409 with the codes `invalid_connector_config` and `connector_destination_not_allowed`; the same conditions at save time are a 422 because there the bad value is in the request body. A prohibited destination discovered while a job runs (`egress_denied`) and upstream failures (`source_unavailable`, `source_unauthorized`, ...) are not HTTP errors of the sync request at all: they are the job's fixed failure codes, because the request was accepted. This was reviewed in the post-11A follow-up and kept: the choice follows these semantics, not a test's assumption, and the operation is new (no existing contract changed).

## Tenant isolation
The connector is looked up inside the caller's tenant (RLS plus a tenant predicate). The worker runs every record write in a tenant-scoped session; `connector_sync_records` has forced RLS, a tenant-scoped worker policy and column-limited grants, and the worker received INSERT on `document_sources` for the same tenant-scoped use. No RLS bypass exists anywhere in this path.

## Mock source
`mock-services/records` (port 8106 when started by `scripts/dev.py` or the demo launcher): cursor, offset and page endpoints over fictional Apex notes and Meridian bulletins, `X-API-Key` authentication, and controllable failures (429 with Retry-After, 503, slow response, bad shape, URL-like and repeated cursors, empty page with continuation, redirect). The live checkpoint is `python scripts/demo.py smoke --rest --no-browser --backup` (a run-only API key is generated for the run and never written anywhere).

## Limits
The Data Sources page can start a synchronisation (administrators; the API also allows supervisors) and shows recent jobs; Integration Health runs the live probe on request. One connector kind (`rest`) with GET pulls; the limiter, pagination and probe are not applied to the ticketing, inventory, CRM or fleet clients. No scheduling: a synchronisation runs when requested. The failure exercised live is a controlled injection, not a real outage. Webhooks and CSV connectors are Batch 11B.
