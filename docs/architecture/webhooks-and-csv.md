# Signed inbound webhooks and the CSV connector (Batch 11B)

Added in Batch 11B (migration `0013`) on top of the REST pull ingestion of Batch 11A ([rest-ingestion.md](rest-ingestion.md)). Requirements touched: V41-12.01 (webhook payloads and CSV records), V41-11.01 (CSV and webhook connectors), V41-11.02 (capabilities evaluated against the new connectors). Everything reuses the existing ingestion jobs, retained original sources, per-record idempotency and tombstones, RLS, worker, audit and egress controls; there is no second ingestion framework.

## CSV connector
A connector of kind `csv` whose `config.csv` names one file (`path` on the connector's own base URL), the `id_field` column, optional `version_field` and `required_fields`, and bounds (`max_rows` default 1000, cap 5000; `max_bytes` default 1 MiB, cap 5 MiB; `max_cell_bytes`; `max_record_bytes`; `delimiter` of `,`, `;` or tab; `reject_policy`). It is synchronised with the same operation, job and worker as REST: `POST /connectors/{id}/sync`, outcome in `GET /ingestion/jobs`.

The file is fetched with the existing `HttpConnector` (per-request egress policy, no redirects, key from `secret_ref`, rate limiter, `Retry-After`, bounded retries) in raw mode, then parsed deterministically: UTF-8 only (with or without a BOM; anything else is `source_schema_invalid`), NUL bytes refused, a header is required with unique valid names and the id column, blank rows skipped, rows with the wrong number of cells or invalid quoting rejected and counted (`malformed_row`, never guessed), an oversize cell makes its row malformed, rows beyond `max_rows` end the pull as `synced_truncated`. Each valid row becomes one document through the same pipeline as a REST record (retained original, `store_parsed`, `connector_sync_records`).

**Provenance:** the source record identifier (the id column, stable across file reordering) decides identity, and the data row number of the last file is stored beside it (`source_row`), so inserting a row at the top shifts every row number but changes no record. **Formulas:** cell values stay text and are never evaluated; the platform never writes CSV or spreadsheets from this content, so there is no export path where a leading `=`, `+`, `-` or `@` could be interpreted (a test stores such cells verbatim). Any future export feature must neutralise those prefixes.

## Signed webhooks
**Provisioning (tenant administrator only).** `POST /webhook-endpoints` creates an endpoint: a name, the **name of the server environment variable** that holds the HMAC signing secret (`secret_ref`; the secret itself is never supplied, stored or returned) and a configuration (`id_field`, `version_field`, `required_fields`, optional `record_path`, `document_kind`, `max_records`, `reject_policy`; fixed at creation). The response carries an unguessable `receive_path` (`/api/v1/webhooks/{endpoint_id}`). `GET /webhook-endpoints` lists them. `PATCH /webhook-endpoints/{id}` disables or re-enables an endpoint and rotates the secret: naming a new variable keeps the old one acceptable (`has_previous_secret`) until `drop_previous_secret` is set. Every change is audited.

**Trust model.** A delivery carries no token. The tenant is found only from the endpoint id in the URL through the narrow `webhook_endpoint_lookup(uuid)` database function (the single, deliberate pre-authentication lookup: it takes one id, returns the tenant, the secret reference names, the status and the configuration, cannot enumerate, and is callable only by the application role). The body and headers never name a tenant; a `tenant_id` field in a payload, or `X-Tenant-*` headers, are ignored (tested). All later work runs in a tenant-scoped session with RLS.

`webhook_endpoints` has RLS enabled and is an [owner-approved FORCE exception](../security/identity-tables.md#owner-security-disposition-for-gate-c). The owner-executed definer lookup is the bounded exception to ordinary tenant-scoped access. App and worker direct table access remains subject to tenant RLS. The delivery ledger uses FORCE RLS.

**Delivery (`POST /api/v1/webhooks/{endpoint_id}`), in this order:** (1) `Content-Type: application/json` (415 otherwise); (2) size: declared length and a bounded streaming read, at most 256 KiB, nothing larger is ever buffered (413); (3) a shared pre-lookup rate bucket, then the endpoint's own bucket (20 per second, burst 40; 429 with `Retry-After`; process-local, **not distributed**); (4) endpoint lookup; (5) HMAC-SHA256 over `timestamp.delivery_id.raw_body` (headers `X-Webhook-Signature: sha256=<hex>`, `X-Webhook-Timestamp`, `X-Webhook-Delivery-Id`) using the raw bytes and `hmac.compare_digest` against the current and the previous secret; the delivery id is part of the signed string so a captured signature cannot be replayed under a new id; (6) only after the signature is proven, the timestamp window (±300 s; `timestamp_out_of_window`), so the window is no oracle for anonymous callers; (7) payload validation (JSON, shape, record count against the endpoint configuration; 422 `invalid_payload`); (8) **one transaction**: the replay ledger insert (`UNIQUE (endpoint, delivery id)` decides atomically), the raw body as a retained original, the durable `webhook` job (idempotency key `webhook:<endpoint>:<delivery id>`) and the audit event; **202 is returned only after that transaction commits**.

**Failure semantics.** Unknown endpoint, disabled endpoint, missing or malformed headers, wrong secret, tampered body, tampered delivery id and tampered timestamp all produce the identical `401 invalid_signature` (tested to be indistinguishable). A secret variable missing on the server fails closed (`503 webhook_not_configured`). A replayed delivery id (even freshly signed, even with a different body) is `409 webhook_replayed`; a delivery that passed authentication but can never be processed is recorded (the id is consumed) and answered 422. The replay ledger is append-only for the application (no UPDATE or DELETE privilege) and rows are small; there is no purge in this version.

**202 means "durably queued", never "processed".** The worker processes the delivery through the same per-record pipeline as REST and CSV: it re-reads the stored body (checksum verified), validates every record, and ingests each with per-record idempotency (unchanged skipped, changed becomes a new version, a record repeated inside one delivery counted), provenance (source record id, endpoint id, delivery job) and **tombstones** (a record whose document the customer deleted stays deleted even if a later delivery changes it: `tombstoned_changed`). The raw delivery body is released when the job completes (each record keeps its own retained original). Failed jobs follow the existing retry rules; an invalid body is a permanent failure that keeps nothing.

**Audit.** Authenticated outcomes are audited without content: `webhook.delivery_accepted`, `webhook.delivery_processed`, `webhook.delivery_replayed`, `webhook.delivery_rejected`, `webhook.endpoint_created`, `webhook.endpoint_updated`. Signature failures are counted (`webhook_deliveries_total{outcome=rejected_*}`) and logged but deliberately **not written to the audit log**: an anonymous caller must not be able to flood a tenant's audit trail.

## Deployment posture
The receiver is a normal API route on the loopback-bound development server; nothing in this repository exposes it publicly, and a public deployment would need a reverse proxy or gateway in front of it (TLS, a distributed rate limit, network allow-listing), which is out of scope and not claimed.

## User interface
The Data Sources page (tenant administrators) lists webhook endpoints with their receive path, status and whether the server has the secret, creates endpoints (only the NAME of the signing-secret variable is entered), disables or enables them, rotates the secret with an overlap and drops the previous one; the same page shows recent synchronisations and deliveries as counts. Vitest covers validation, confirmation and the role rules; a Playwright test provisions an endpoint, sends a real signed delivery to the isolated stack, sees it processed and checks that a disabled endpoint rejects it.
