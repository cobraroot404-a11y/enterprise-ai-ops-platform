# Phase 8 requirements and implementation gap audit

Source: `docs/traceability/requirements-traceability-matrix.json` (generated from `scripts/traceability_data.py`), re-read against the repository on the Phase 8 start commit.

## Reconciliation of the reported counts

The matrix holds **85** requirements: **55 verified, 22 partially verified, 8 not implemented**. These match the Phase 7 report exactly; no requirement is silently reclassified in this phase.

## Findings the audit must disclose

1. **Requirement identifiers.** The `R<part>.<n>` identifiers are this project's own catalogue ids (specification part number plus sequence). Only the FI-01..FI-10 and UAT-A01..B07 identifiers are the specification's own. The V4.1 specification text is not stored in the repository, so completeness of the catalogue against the full specification text cannot be proven by this audit. **Action requested at Gate B:** supply the specification file (or confirm it may be added under `docs/`) so each catalogue id can be mapped to the exact clause.
2. **Possible omissions.** Bullet-level requirements in specification parts 4, 28, 31 and 34 (priorities, repository layout, roadmap, final audit) are only covered coarsely (R2, R29, R32, R33). Phase 8 will split them once the specification text is available.
3. **Evidence strength varies.** Several 'verified' requirements rest on one scenario in a synthetic environment (for example R16.1 tenant isolation is verified through the application and PostgreSQL RLS, but not against a compromised application process). The limitation column in the matrix carries these caveats.
4. **Implementation-versus-specification conflicts recorded:** no ingestion jobs/evaluation-run/roles tables (R17.3), no document deletion (R12.5), no CSV/webhook connector kinds beyond names (R11.4), and Apex runs on built-in rules while Meridian is profile-driven (documented technical debt, `docs/architecture/apex-meridian-execution-paths.md`).
