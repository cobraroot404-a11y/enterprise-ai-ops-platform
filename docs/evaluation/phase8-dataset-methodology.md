## v1.0 text (draft, pending Gate B approval at that time)

All content is **synthetic**. Apex Industrial Manufacturing and Meridian Fleet Logistics are fictional and no real customer data, systems or outcomes are represented.
`apex-eval-v1` (60 queries, 24 fault reports, 86 chunks) and its Phase 3/4 results stay untouched. A known defect in v1 is recorded, not edited: its `dataset_manifest.json`
field `queries` reads 4 while `queries.jsonl` holds 60 lines; v2 manifests are generated from the files and checked by a test.

## 1. Why v2 (what v1 cannot show)
One relevant passage per query (Precision@5 ceiling 0.2), an 86-chunk corpus (Recall@5 saturates at 100%), shared vocabulary between queries and sources, no hard negatives, no
superseded versions, only 12 unanswerable queries (8 in test), Apex only. Test-split precision is therefore about +-10 percentage points per proportion.

## 2. Corpus design (per tenant, generated by a deterministic, seeded, committed script)
| Source type | Apex | Meridian |
|---|---|---|
| Equipment/vehicle manuals (PDF), several models per family with near-identical wording | 10 manuals, 2 versions for 3 of them (v1 superseded, v2 current, changed limits) | 8 manuals, 2 versions for 2 of them |
| Maintenance procedures / troubleshooting guides (PDF) | 6 | 6 |
| Inspection reports and operational logs (PDF/CSV) | 6 | 6 |
| Asset or vehicle register (CSV) | 1 (about 60 assets with deliberately similar ids, e.g. P-101/P-110/P-1010) | 1 (about 60 vehicles, e.g. VH-2101/VH-2110/VH-2011) |
| Historical incidents / service records (CSV) | about 120 records | about 120 records |
| Poisoned passages (injected instructions inside otherwise plausible text) | 6 | 6 |
Target size: about 700 chunks per tenant (v1: 86 in total). Conflicting records (two records disagreeing on a limit) and outdated versions are deliberate and labelled.
Document wording is produced from varied, independently authored fact tables with several surface realisations each, to avoid one-template-per-fact answers.

## 3. Query and incident sets (targets, not achievements)
| Set | Target | Notes |

| Unanswerable / insufficient evidence | >= 45 | include topically close but unsupported, and answer-exists-only-in-another-tenant |
| Hard multi-relevant (2-4 relevant passages, hard negatives) | >= 32 | |

| Version-conflict queries | >= 16 | answer exists only in the current version |

Categories overlap; the manifest lists unique counts and the overlap matrix. If the corpus cannot support these counts without duplicated templates, the smaller defensible number is proposed instead.

## 4. Annotation
Each item records: `id`, `tenant`, `dataset_version`, `category`, `difficulty` (easy/medium/hard by a pre-declared rule: number of distractors sharing the key terms), `answerable`, `required_facts`,
`relevant` (passage ids with grade 2 essential / 1 supporting), `evidence_spans` (exact character offsets verified by script), `citation_expectation`, `expected_refusal`, `expected_asset_id`,
`expected_category`, `expected_priority`, `review_expectation` (must_review / may_clear), `safety_tags`. Labels are written by the dataset generator from the fact tables **before** any model run;
the generator, not a model, decides the label. Ids are stable (`E2-A-0001` style).

**Label quality, stated honestly.** The author of the dataset and labels is the same party (this AI-assisted project); there is no independent expert annotator. Controls: (1) a script checks every
evidence span exists verbatim in the current corpus and that each required fact appears in a labelled span; (2) a rubric (`docs/evaluation/phase8-annotation-rubric.md`, written with the dataset) defines
relevant / supporting / unanswerable and tie-breaking; (3) ambiguous items are tagged `ambiguous`, adjudicated by rule and listed; (4) a **blind re-annotation pass**: a second, independently prompted
pass labels a random 25% sample from the documents only and agreement (Cohen's kappa for relevance, exact match for facts) is reported. A second pass by an AI is *not* independent human validation and will
be reported as a consistency check. **If you can review a sample (suggested: 30 items), that would give genuine human validation; this is requested at Gate B.**

## 5. Splits and leakage control
Three splits: `dev` (about 55%, tuning), `test` (about 35%, frozen, evaluated once), `challenge` (about 10%, adversarial/hard cases, evaluated once after test).
- The unit of splitting is the **scenario family** (a fact plus all its paraphrases, hard negatives, related incident reports and extraction cases), so near-duplicate queries and shared answer templates never cross splits.
- The corpus is shared across splits because the simulated knowledge base is one corpus; this is *shared-corpus retrieval*, not query leakage, and is documented. Test-only facts exist only in documents no dev query targets, but
  dev tuning sees the whole index (as production would). Chunking/retrieval parameters are therefore tuned on dev queries only.
- Hashes (SHA-256) of the corpus files, `queries.jsonl`, `incidents.jsonl`, qrels and the split manifest are written to `evaluation/datasets/eval-v2/MANIFEST.sha256` and the test split is frozen (hash recorded in git) **before any optimisation**.
- Held-out failures are not inspected for tuning. If a test item is viewed for diagnosis, the exposure is disclosed in the report and the claim of unbiased test results is withdrawn; a fresh untouched test set would be needed, and
  no second final benchmark is run on a modified test set merely to improve results.
- Tests: no id or normalised query string appears in two splits; a similarity check (token Jaccard and embedding cosine against the MiniLM model already installed) flags cross-split near-duplicates above a stated threshold; labels never reference model outputs.

## 6. Reproducibility
The generator is seeded and deterministic; the same seed produces byte-identical text files (PDF rendering is checked by content hash of the extracted text, since PDF bytes can embed timestamps). Commands, versions and hashes are recorded in `evaluation/reports/phase8/`.
