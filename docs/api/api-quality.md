# API quality verification (V41-17.03)

Requirement V41-17.03 asks for nine API-quality properties: typed contracts, validation, pagination, standardized errors, OpenAPI documentation, database migrations, transactions, constraints and indexes. This page says what is verified, how to reproduce it, and what is still open. Evidence is same-author and local; it is not a production-readiness claim.

## What is verified (suite `backend/tests/test_api_contract.py`, tests named `test_pN_*`)
| Property | Verified by | Result |
|---|---|---|
| P1 Typed contracts | every request body references a typed schema; **every success response of all 45 operations declares a typed object schema** (Batch 3: 41 stable JSON operations, 4 whose content depends on external data, all typed); every runtime response is validated against its declared schema by an independent validator that also rejects undeclared keys; the runtime shapes equal the pre-change baseline | verified |
| P2 Validation | generic wrong-shape fuzz over every JSON-body route (no 500 anywhere), field-level checks on incident extraction (missing, too short, too long, wrong type, bad enum, bad nested record), malformed JSON, bad UUIDs, enums, oversize body (413), invalid upload kind | verified |
| P3 Pagination | every list endpoint (documents, incidents, tickets, approvals pending and decided, workflows, audit, platform audit) has the same `{total, limit, offset, items}` envelope, stable ordering, disjoint and complete pages, empty page beyond the total, bounds (`limit` 1..100, `offset` >= 0) enforced with 422, per-tenant scoping | verified |
| P4 Standardized errors | 401, 403, 404, 405, 409, 422, 413 and 500 all use `{"error": {"code", "message", "correlation_id"}}` with a matching `X-Correlation-ID` header, no stack traces or internals, supplied correlation ids are echoed | verified |

## Defects found and fixed by this batch (API layer only)
1. Unknown paths and wrong methods returned the framework body `{"detail": ...}`; they now use the standard error body (`not_found`, `method_not_allowed`).
2. OpenAPI declared no security scheme; it now declares `bearerAuth` and marks every non-public operation as protected (login and health stay public).
3. An unhandled internal error returned a 500 without the `X-Correlation-ID` header; the header is now set.
4. `GET /platform/audit` had no `offset`, `total` or bounds (it clamped `limit` silently); it now has the common envelope and validated bounds (additive; the frontend reads only `items`).

## Typed responses V41-17.03-TYPED-RESPONSES (closed in Batch 3)
Batch 2 found that no operation declared a typed success response. Batch 3 added `backend/app/api/v1/response_models.py` and `response_model=..., response_model_exclude_unset=True` on all 45 operations. `exclude_unset` keeps omitted keys omitted and explicit nulls null, so the JSON is unchanged: `backend/tests/test_api_response_contract.py` compares 49 pre-change runtime captures (status, content type, headers, structural shape, enum values, uuid/timestamp formats) with the current responses and fails on any difference; `backend/tests/test_api_response_schemas.py` validates every capture against the declared OpenAPI schema. Free-form JSON is limited to a documented set (`FREE_FORM_EXCEPTIONS`: audit/history details, connector config, metric label maps). Inventory: `docs/api/response-inventory.md`. The strict expected failure was converted into a normal passing test only after it flipped to XPASS.

## Error contract (Batch 3.1, metadata only)
`backend/app/api/v1/error_contracts.py` types the standardized envelope (`ErrorResponse` / `ErrorInfo` / `ErrorDetail`; `SizeLimitErrorResponse` for the 413 body produced by the size-limit middleware) and declares, per operation, the error statuses it emits (`ERROR_STATUSES`), with `X-Correlation-ID` on every error response and `Retry-After` on 429 and 503. FastAPI's default 422 `HTTPValidationError` is no longer published, because the application answers validation failures with the standardized envelope. Runtime bodies, status codes, handlers and authorization are unchanged. `backend/tests/test_api_error_contract.py` drives every operation through failure scenarios (`backend/tests/api_error_probes.py`: credentials, each role, unknown ids, invalid bodies and parameters, oversize bodies and files, state conflicts, duplicates, throttling, concurrency limits, unsupported uploads, injected database and internal failures), validates each observed body and header against the documented schema, and checks the status table in both directions (nothing declared that no scenario produced, nothing produced that is undeclared). Success statuses: 39 operations return 200 and 6 return 201 (tenant creation, member creation, connector creation, document upload, incident extraction, ticket creation); the earlier "40 / 5" statement in the Batch 3 report was a prose error and is corrected there.

## Index defect V41-17.03-IDX (closed in Batch 2)
Batch 1 recorded that `incidents`, `approvals` and `outbox_events` had no tenant-leading index and kept the check as a strict expected failure. Migration `0008_tenant_leading_indexes` adds `incidents (tenant_id, created_at DESC)`, `approvals (tenant_id, decided_at DESC)` and `outbox_events (tenant_id, id DESC)`; the strict marker flipped to XPASS and was then converted to a normal passing test. Migration tests, query-plan evidence and the rationale are in `docs/planning/batch2-report.md`.

## Known limits
Handlers still return plain dictionaries; the response models validate and document them at the framework boundary (an undeclared or ill-typed value would raise a server error, so the conformance tests exist to catch drift). Class E operations (evaluation reports, observability summary, metrics, tenant profile) are typed but their content comes from external data. Error responses are documented per operation in OpenAPI since Batch 3.1 (see below); the 413 size-limit body carries no `correlation_id` in the body (the header is set), and error codes are an open vocabulary listed in the response descriptions. The ORM maps a subset of the schema (indexes, constraints and RLS live in the migrations), so the drift check is one-directional by design. The suite is same-author.
