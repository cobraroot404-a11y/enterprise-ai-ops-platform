## Design
**Connector.** Existing `connectors` row, kind `rest`, whose `config` has a `records` object (a connector without it behaves exactly as before). `base_url` is the only network destination: every request goes through the existing `HttpConnector` (per-request egress policy, pinned address, no redirects). A path is a relative string that must start with `/` and contain no scheme, authority, `..` or backslash; pagination values are tokens, never URLs (a cursor containing `://`, `//` or a backslash is rejected). Authentication: the existing `X-API-Key` from `secret_ref` (environment variable name); a connector that names a secret that is not set fails before any request (`credentials_missing`); headers and tokens are never logged or returned.

**Config (`config.records`, validated at creation and again at sync):** `path`, `record_path` (JSON key of the record list, default `items`), `id_field` (required: stable source ids are never invented), `version_field` (optional update marker), `required_fields`, `document_kind`, `pagination` {`mode`: `cursor`|`offset`|`page`|`none`, `page_size`, parameter names, `next_cursor_field`, `has_more_field`, `total_field`}, `max_pages` (default 20, cap 100), `max_records` (default 500, cap 5000), `max_record_bytes` (default 64 KiB), `reject_policy` (`skip` default, or `fail`), `rate` {`requests_per_second` 0.1 to 50, `burst` 1 to 20}.

**Pagination.** cursor (token from `next_cursor_field`; empty means end; `has_more_field` true without a token is `missing_continuation`; a repeated token is `pagination_loop`; invalid characters or URL-like tokens are `invalid_cursor`), offset (advance by records received; ends on an empty or short page or at `total_field`), page (1-based; same endings), none (one request). All loops are bounded by `max_pages`, `max_records`, a 1 MiB response limit (existing) and detection of an identical repeated page. Unexpected shapes (record list missing or not a list, record not an object) are permanent `source_schema_invalid`.

**Rate limiting.** A token bucket per `(tenant, connector)` held in the process (`connectors/ratelimit.py`): configurable rate and burst, waiting uses a condition with a timeout (no busy wait), a total wait bound, a stop event for shutdown/cancellation, no shared state between tenants. HTTP 429 and 503 carry `Retry-After` (seconds, clamped to 30 s) which pauses the bucket; after bounded attempts the page fails transiently and the job retries with backoff. **Process-local only: not distributed rate limiting; V41-16.04 stays Partial.**

**Health probe (opt-in).** `GET /connectors/health?probe=true` (existing route, additive parameter, `connectors:write` role): for each `rest` connector with `config.records`, one bounded GET (3 s, no retry, one record requested, nothing ingested, nothing changed upstream) through the same egress and credential path. Result classes: `ok`, `connectivity`, `authentication`, `rate_limited`, `schema`, `upstream_error`, `denied`, `not_configured`; sanitised detail only; an audit event `connector.probed` records the class. Without `probe=true` the endpoint is unchanged and makes no network call.

**Durable job (no second framework).** `ingestion_jobs` gets job type `sync`, `connector_id` and a `progress` JSON (cursor/offset/page position, pages, counts). `POST /connectors/{id}/sync` (new role `connectors:sync`: administrator and supervisor) commits a `sync` job (idempotency key `sync:<connector id>`: a second request while one is active returns that job) and answers `202` with the job. The existing worker claims it (fenced lease, now renewable per page), pulls pages through the connector, and processes each valid record before moving on; progress is saved after every page; transient failures (network, 429/5xx, embedding) retry with the existing bounded backoff and resume from the saved position; permanent failures (config, schema, credentials, egress, loops) fail. Terminal states reuse COMPLETED/FAILED/CANCELLED. Outcome `synced` (all records valid) or `synced_with_rejections` (counts reported honestly); success is recorded only after every page was processed.

**Record to document.** One document per source record: file name `rest-<connector>-<record id>.json`, the record serialised canonically as a one-element JSON array, stored as a retained original (`document_sources`, parse option `id_field`) and ingested by the existing parser and `store_parsed`, so chunks carry the source record id (provenance), reprocessing from source works, and deletion cleanup covers it.

**Idempotency and provenance (`connector_sync_records`, migration 0012).** One row per `(tenant, connector, source record id)`: content SHA-256, source version marker (when supplied), document id and version, last job id, status (`active`, `deleted`), timestamps. A repeat sync compares the hash: unchanged means nothing is stored; changed becomes a new version of the same document; unseen is created; identical content that already exists as another document is linked, not duplicated; a record that repeats inside one sync with different content keeps the first and is counted as a conflict. A document deleted by a user marks its row `deleted` and stays deleted until the source record's content changes. Every per-record write re-locks the job claim (fenced), the sync row and the document and refuses a deleted one, so a stale or concurrent sync cannot resurrect it.

**Tenant security.** Connector looked up by id inside the caller's tenant (RLS plus predicate): unknown and other-tenant ids are 404. The worker runs every record write in a tenant-scoped session; `connector_sync_records` has forced RLS and a tenant-scoped worker policy with column-limited grants. Destination, credentials and path come only from the stored connector; the request body of the sync operation is empty. Audit events carry counts and ids, never content or credentials.

## Database (migration 0012, additive)
Job type CHECK widened to include `sync`; `ingestion_jobs.connector_id`, `ingestion_jobs.progress`; table `connector_sync_records` (RLS, indexes, unique key); worker grants. Downgrade refuses while sync jobs or records exist.

## API (one new operation)
`POST /api/v1/connectors/{connector_id}/sync` (202, `IngestionJobOut`; 401, 403, 404, 409, 500, 503). Amendment made during implementation: a connector that cannot be synchronised (invalid configuration, unapproved destination) is a 409 conflict with the resource state rather than a 422, because the repository's API-quality contract reserves 422 for operations with a request body or query parameters. Additive: `probe` query parameter on `GET /connectors/health`; optional `connector_id` and `sync` fields on `IngestionJobOut`. No webhook, endpoint-management or CSV operation. No frontend change.

## Mock source
