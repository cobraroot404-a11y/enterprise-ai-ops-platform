# Batch 9 architecture manifest (written before implementation)

Requirements: V41-12.03 "Retry handling" (acceptance: "Failed ingestions are retried safely") and V41-12.04 "Reprocessing" (acceptance: "Documents can be reprocessed"), original specification line 495 and 496, list "... Idempotent ingestion, Retry handling, Reprocessing, Deletion, Reindexing". Specification SHA-256 verified. Starting point: HEAD `05265f7`, migration head `0009`. No conflict with the specification or an existing public contract was found: uploads stay **synchronous** (same 201 body, same 503 `embedding_unavailable` with `Retry-After` on a transient failure).

## Design
- **Persistent job**: new table `ingestion_jobs` (migration 0010): id, tenant_id, job_type (`ingest` | `reprocess`), status, document_id, source_version, attempts, max_attempts, next_attempt_at, claim_token and locked_until (fencing lease), claimed_by, error_code, error_detail (sanitised, no content), idempotency_key, requested_by, correlation_id, payload (parsed segments of a new upload, kept only while the job can still run, nulled at any terminal state), outcome counters, timestamps. A **partial unique index** on (tenant, idempotency_key) for active states makes duplicate submission return the existing job.
- **State machine** (server-controlled; clients and models cannot set a state): QUEUED -> PROCESSING; PROCESSING -> COMPLETED | RETRY_PENDING | FAILED | CANCELLED; RETRY_PENDING -> PROCESSING | CANCELLED; QUEUED -> CANCELLED; FAILED -> QUEUED (authorised manual retry, reprocess jobs only); COMPLETED and CANCELLED are final. Transient failures (embedding model unavailable, database connectivity) retry with bounded exponential backoff up to `max_attempts` (5) then FAILED(`retries_exhausted`); permanent failures (unsupported or invalid content, validation) go straight to FAILED. Claims use `FOR UPDATE SKIP LOCKED` with a lease; a worker that dies leaves a PROCESSING row whose lease expires and which is reclaimed (the lost attempt counts); the final write re-checks the claim token and the document lifecycle under row locks (stale workers cannot overwrite; a deleted document cannot be revived).
- **No second framework**: the job table is the queue (it needs per-job state the outbox row cannot hold) and the **existing worker loop** (`process_one`) drains it after ticket submissions and document cleanups, with the same claim pattern, lease, backoff helper and tenant-scoped sessions.
- **Upload (unchanged contract)**: parse, then record a job and process inline. Success: document, version, chunks and job COMPLETED commit together. Transient failure: job persisted RETRY_PENDING (with the parsed segments), response 503 as before; the worker completes it later or the client's repeat upload resumes the same job (idempotent). Permanent failure: job FAILED, same error response as before.
- **Reprocessing (explicit, authorised)**: `POST /documents/{id}/reprocess` (tenant administrator, supervisor) queues a job. It re-derives the current version's chunks from the stored parsed segments (re-embeds with the active profile, re-evaluates the injection heuristics) as a **new generation** of chunks staged non-current, validates counts, lineage and vectors, and activates the new generation and retires the old one in one transaction. Old-generation chunks stay stored (not current), so historical citations keep their meaning and a failed attempt can never damage the active content. Original uploaded bytes are not stored and not needed.
- **Deletion interaction**: deleting a document cancels its active jobs; every final write (store, activation) re-locks the document row and refuses a non-active document; a job can never reactivate a deleted document; cleanup (Batch 8) removes all generations.

## Database changes (migration 0010, additive)
`ingestion_jobs` (+ RLS tenant policy for the app role, worker policy and column-limited grants, indexes, CHECK constraints); `document_chunks.generation int not null default 1`; `document_versions.active_generation int not null default 1`; worker privileges needed to store content (INSERT and limited UPDATE on documents, versions, chunks, embedding_profiles, all tenant-scoped by policy). Existing rows keep generation 1. Downgrade refuses while any job exists beyond the defaults or any generation > 1 exists (evidence would be lost).

## API changes (all new, typed, tenant-scoped; existing operations unchanged)
GET /ingestion/jobs (page; filters status, job_type, document_id), GET /ingestion/jobs/{job_id}, POST /documents/{document_id}/reprocess (202), POST /ingestion/jobs/{job_id}/retry (202). Existing `POST /documents`, listings and deletion behave as before.

## Tests and expected effects
Job creation and state transitions, success, retry scheduling and exhaustion, permanent failure, worker interruption at each stage, concurrent claims, idempotent re-execution, duplicate submission, reprocessing success and failure with the prior version preserved, lineage, retrieval exclusion of staged content, tenant authorisation and worker isolation, deletion races, audit, API backward compatibility. Expected compatibility effects: operation count 46 -> 50 (pinned counts updated), the existing REL-02 fault-injection behaviour preserved (503, nothing becomes active), no change to existing response fields.
