## 3. Implementation (bounded groups; all in one reviewable module)
`backend/app/api/v1/response_models.py` (67 models) and `response_model=..., response_model_exclude_unset=True` on all 45 operations. Group A shared: `Page[T]` envelope, `UUIDStr`/`DateTimeStr` (plain strings with an OpenAPI format, so nothing is re-parsed), `Number` (int or float, so integers are never turned into floats). Group B core: incidents (with citations, related incidents and measurement records), tickets, approvals (pending and decided), human-review and measurement-verify results, workflow events. Group C supporting: documents, ingestion status, search, ask, audit, history, metrics, observability, evaluation. Group D remaining: login and session, tenants, members, connectors and their health, tenant profile, onboarding health, health. `exclude_unset` keeps omitted keys omitted and explicit nulls null, so the JSON is unchanged. Closed vocabularies enforced by the database or the code are `Literal` types.
**Design decisions made during the batch (disclosed):** (a) with default Pydantic settings an undeclared key a handler adds later would be silently dropped from the response and invisible to a conformance check; response models therefore pass extras through at runtime but publish a **closed** schema (`additionalProperties: false`), so drift is reported by the tests instead of lost; models that deliberately describe open stored JSON are listed in `OPEN_MODELS` and published open. (b) The domain `Citation` and `RelatedIncident` models were not reused as response types (they are not closed); response-side `CitationOut` and `RelatedIncidentOut` carry the same fields. (c) The tenant profile reuses its own validated `TenantProfile` schema (listed in `EXTERNAL_MODELS`).

## 5. Runtime compatibility and schema accuracy results
- All 49 baseline entries equal the current responses (status, content type, headers, shape). 
- Every runtime response (the 45 operations plus 11 added variants: structured submission, rejected structured record, no-number candidate, empty pages, filtered audit, non-administrator onboarding health, Meridian profile and connectors) validates against its declared OpenAPI schema with an independent validator (types, required keys, nullable unions, nesting, arrays, enums, uuid and date-time formats, strict rejection of undeclared keys). The validator's own detection power is tested (undeclared key, missing key, wrong type, enum and format violations).
- Every success schema resolves to a real object schema with properties (a bare `$ref` or empty schema is rejected); the six creating operations document 201 and the rest 200.
- No response exposes credential or secret fields (scan of all captured bodies and of the declared schemas); error bodies are unchanged and standardized.
- **Defect caught by the existing suite during the batch:** the onboarding checklist can report `unavailable` for non-administrators; my first model declared only `pass` or `fail`, which would have produced a 500. It was fixed and the variant added to the harness. Every other closed vocabulary was checked against the code (health `ok`; review status four values; connector status `ok`/`blocked`/`degraded`; ticket, outbox, priority and decision values are enforced by database constraints). This is the main residual risk of `response_model`: a value outside a declared `Literal` becomes a server error rather than a silently wrong document; the conformance tests and the full suite are the guard.

## 10. Remaining defects and limitations
1. **OpenAPI error documentation (closed in Batch 3.1, see `docs/planning/batch3_1-report.md`):** the 422 response declared per operation is FastAPI's default `HTTPValidationError`, while the API actually returns the standardized `{"error": {...}}` body (verified by the standardized-error tests). Success responses are fully typed; error responses are documented by tests, not by OpenAPI schemas. A small non-breaking follow-up (declare the standard error model for 401, 403, 404, 409, 422) would close this. 
2. Handlers still return plain dictionaries; typing happens at the framework boundary.
3. Class E operations are typed but depend on external data; `Literal` vocabularies can turn an unforeseen value into a server error.
4. Frontend consumer search is textual. Same-author evidence.
