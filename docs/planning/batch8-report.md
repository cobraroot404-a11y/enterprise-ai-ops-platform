## 2. Lifecycle and dependency map (prepared before coding; final form in [document-lifecycle.md](../architecture/document-lifecycle.md))
Document text lives only in `document_chunks` (text, embedding, tsv); `document_versions` hold hash and size; there is no file store (no content files or storage references exist) and no retrieval or result cache (only model-client caches). Chunks are read by raw SQL in `retrieval/search.py`, `retrieval/entities.py`, `ai/safeguards.py` and `services/incident_service.py`; incidents copy chunk quotes into `citations` and `related_incidents` (JSON); tickets, approvals and the audit log reference documents only by id or filename. The shared outbox and worker (role `eaop_worker`, previously no access to document tables) are reused for cleanup.

## 3. Final deletion policy (as implemented)
**Stage A, in the request, one transaction:** server-controlled `lifecycle_status = deleted`, actor and time recorded, chunks no longer current, version content hashes and the document's name released (a later upload of the same name or bytes is a new document), one `document.cleanup` outbox event, one content-free audit event. **Stage B, worker, tenant-scoped, one transaction:** redact quotes and summaries copied into incident citations and related incidents, delete chunks (text and embeddings) and versions, verify none remain, then mark `completed`; failure rolls back and retries; exhausted retries mark `failed` and a repeated delete request re-queues. Kept deliberately: the document tombstone (id, tenant, filename, kind, actor, times, state), all audit events (outcome, state and counts only, never text), incidents, tickets and approvals. Authorization: `documents:delete` for tenant administrator and maintenance supervisor (design choice: deletion is consequential, so engineers and auditors are refused).

## 4. Migration 0009 (inspected head 0008, no historical migration touched)
Adds `documents.lifecycle_status` (default `active`, so every existing row is preserved unchanged), `deleted_at`, `deleted_by`, `cleanup_state`, `cleanup_completed_at`, three CHECK constraints (including one tying the columns together), and the minimum worker access: SELECT on documents, UPDATE of `cleanup_state` and `cleanup_completed_at` only, SELECT and DELETE on chunks and versions, UPDATE of `incidents.citations` and `related_incidents` only, and **tenant-scoped** RLS policies for the worker on the three document tables. Downgrade refuses while any document is deleted (it would discard evidence). Evidence (`test_migration_0009_document_lifecycle.py`, 5 passed, on a disposable database): existing documents preserved as active, only the five columns added, every inconsistent row rejected by the constraints, worker privileges exactly as designed (cannot revive a document, cannot see another tenant, no cross-tenant visibility without context), application-role isolation unchanged, downgrade refusal then restoration then re-apply. **The shared `eaop` database (still at revision `0006`) was not touched.**

## 5. API and authorization behaviour
`DELETE /api/v1/documents/{document_id}` returns 200 with `DocumentDeletion` (`id`, `filename`, `lifecycle_status`, `cleanup_state`, `deleted_at`, `cleanup_completed_at`, `already_deleted`); errors 401, 403, 404, 500, 503 (documented and verified by the existing error-contract probes). Repeat delete: 200 with the current state and `already_deleted: true`, no second audit event or queue entry; a `failed` cleanup is re-queued by the repeat. Unknown, another tenant's and deleted documents are all 404 for reads; another tenant's delete is 404 (never 403, so existence and status cannot be probed). Engineer and auditor: 403 `insufficient_role`; anonymous 401; invalid id 422. The route table, role matrix and error-contract suites were updated for the new operation (counts 46 operations, 40 returning 200, 6 returning 201: each pinned count carries a comment, no assertion weakened); snapshot diff reviewed: exactly the new operation and the `DocumentDeletion` schema.

## 6. Tenant isolation and RLS results (executed)
Another tenant cannot delete, observe, or be affected (its own copy of the same file stays listed, searchable and intact; no audit rows appear for it). The worker role without tenant context sees and can delete nothing; with a tenant context it sees only that tenant; it cannot update `lifecycle_status`. Forged events (this tenant naming another tenant's document; this tenant's still-active document; a nonexistent id) are all refused and marked dead, deleting nothing.

## 7. Retrieval exclusion and citation tests (executed)
Deleted documents disappear immediately, before any cleanup, from listings, `GET /documents/{id}`, counts and ingestion status, and from retrieval in **hybrid, vector and full-text modes**, entity and register lookups, `/ai/ask` citations, citation verification and passage lookup; other documents of the same tenant keep answering. Incident citations and related-incident summaries that came from the deleted document are redacted at read time at once and persisted-redacted by the cleanup, while the incident, its recommended action, its ticket and its history remain. Uploading the same file after deletion creates a **new** document (not "duplicate", not "new_version"). Real-AI tests were **not** run: exclusion is enforced in SQL before ranking and is identical for any embedding backend, and was proved in vector-only mode with the deterministic embedder.

## 8. Cleanup, retry, concurrency and failure recovery (executed)
Successful cleanup with verification and counts; idempotent re-run; partial cleanup failure after the deletes (rolled back, retry scheduled with only the error class stored, then completed); retries exhausted (`cleanup_failed`, content still invisible, repeat delete re-queues, completes); worker crash after claiming (lease expires, event reclaimed); Stage A failure (audit write fails: everything rolled back, document stays active); two simultaneous deletes (serialised: one audit event, one queue entry); an upload racing a deletion (waits for the lock, then creates a new document and cannot add chunks to the deleted one); orphaned and forged events. Missing content files and invalid storage references are not applicable: no files or storage references exist (asserted by a schema test).

## 9. Audit and retention behaviour
`document.deleted` (actor, tenant, correlation id, time; details limited to outcome, cleanup state and the counts of versions and chunks), `document.cleanup_completed` (worker; counts), `document.cleanup_failed` (error class only), `document.cleanup_requeued`. No document text or excerpt appears in any of them (tested). Tickets, approvals and incidents are never erased. Not implemented (not approved): legal-retention or regulatory-erasure policy; text already copied into tickets, external systems, backups (including the demonstration backups) or by hand is not erased; incident fields derived by analysis are retained.
