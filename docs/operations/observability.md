# Observability

Free, local, no paid services.

- **Structured JSON logs** (`backend/app/observability/logging.py`): one event per line with a correlation id (`X-Request-ID`), tenant id,
  route template and event name. Values and keys that look like credentials, bearer tokens, JWTs or API keys are redacted; strings are truncated;
  document text and report text are never logged.
- **Tenant-aware metrics** (`backend/app/observability/metrics.py`): in-process counters and latency summaries labelled with the tenant id only:
  HTTP latency by route, LLM, retrieval and embedding latency, connector calls by outcome (ok/transient/permanent/malformed/denied), submission
  outcomes and retries, ticket transitions, review decisions, AI answer outcomes and error classes.
- **Endpoint:** `GET /api/v1/observability/summary` (`metrics:read`) returns the caller's tenant metrics plus durable database counts (submission
  outcomes, review rates, approvals, transitions, error classes). It is shown in the Integration health page ("Operational telemetry").
- **Evidence:** `python -m pytest tests/acceptance/test_observability_evidence.py -q` runs a real local workflow and writes
  `evaluation/observability/` (summary, redacted sample logs, metadata). The test fails if credential-like patterns appear in the logs.
- **Tests:** `backend/tests/test_observability.py`.

## Durable metrics, trace ids and the Prometheus endpoint (final-completion work)
- **Durable series** (`metric_series`, migration 0015): every process (API, worker) keeps fast in-memory counters and fixed-bucket latency histograms and flushes the **delta** to PostgreSQL every `METRICS_FLUSH_SECONDS` (default 10), at worker exit and before the metrics endpoints read. Deltas from all processes sum; a restart loses nothing that was flushed (at most the last unflushed interval of a crashed process); a failed flush keeps its deltas and never double counts. `GET /api/v1/observability/summary` still shows the in-process view (exact recent samples); the durable view is the `/metrics` endpoint.
- **Prometheus text endpoint:** `GET /metrics` (bearer token with `metrics:read`; outside the typed JSON contract and the OpenAPI schema). It returns the caller's tenant series plus platform-level series, never another tenant's, in text format 0.0.4 with cumulative histogram buckets. Prometheus can scrape it with an `authorization` header; no Prometheus or Grafana is installed or required.
- **Metrics named by the specification:** request latency (`http_request_seconds`), ingestion duration (`ingestion_seconds`, `ingestion_job_seconds`), retrieval latency (`retrieval_seconds`), inference duration (`llm_seconds`), workflow completion time (`workflow_completion_seconds`, creation to external submission), external API failures and calls (`connector_calls_total` by outcome), retry counts (`submission_retries_total`, `ingestion_retries_total`), dead-letter counts (`dead_letters_total` by source), approval turnaround time (`approval_turnaround_seconds`, request to decision).
- **Trace ids:** `X-Trace-ID` on every response, a `trace_id` field on every log line, `traceparent` accepted and sent to upstream services; the id follows a ticket from the approval request through the outbox event to the worker's connector call (`backend/app/observability/tracing.py`).
- **Spans:** `tracing.span(name, **attributes)` times a unit of work inside the current trace and writes ONE structured log event (`event=span`) with `trace_id`, `span_id`, `parent_span_id`, `duration_ms`, `status` and technical attributes. Spans exist for each HTTP request (route template and status), each outbound connector call, each outbox submission and each ingestion job, and nest through the context, so a ticket's approval request, the worker's submission and the call to the ticketing system appear as one linked tree. Outbound `traceparent` carries the current span id as the parent. This is the OpenTelemetry data model written to the existing log stream; it is **not** the OpenTelemetry SDK and nothing exports it (a collector or exporter would be a new dependency and component, and the specification says "where practical").
- **Grafana:** `infrastructure/monitoring/grafana-dashboard.json` is an importable dashboard (12 panels) over the `/metrics` series; a test checks every query against the metrics the code records. Grafana was never installed and the file was never imported.
- **Tests:** `backend/tests/test_durable_metrics.py`, `test_migration_0015_shared_state.py`, `test_observability.py`. `test_spans.py`, `tests/test_grafana_dashboard.py`.

Limitations: durable histograms give approximate percentiles (bucket resolution); other processes' activity can lag the endpoint by one flush interval; there is no sampling and no OpenTelemetry SDK or exporter (spans exist only as log events) (not added: "where practical", and it would add a dependency and a collector for no acceptance criterion); alert rules and dashboards are not provided. The figures are from local runs, not production telemetry.

## What OpenTelemetry interoperability would need (owner approval required; nothing here was installed)
The span events above are **not** OpenTelemetry-interoperable: no OTLP exporter exists, so no OpenTelemetry collector, Jaeger, Tempo or vendor backend can receive them, and the span and trace ids are written in the W3C format but are not created through the OpenTelemetry API. The specification says "where practical", so this was not treated as mandatory. To make it real:
- **Python packages (free, from PyPI over verified HTTPS):** `opentelemetry-sdk==1.45.2` and `opentelemetry-exporter-otlp-proto-http==1.45.2`. `opentelemetry-api==1.45.2` is already in `backend/requirements.lock.txt` (a transitive dependency), so the versions must match it. Together a few hundred kilobytes plus their small dependencies (`protobuf`, `googleapis-common-protos`, `requests`).
- **A receiver, for any demonstration:** the OpenTelemetry Collector (a Go binary, roughly 100 MB) or a Jaeger/Tempo container image. A console exporter in the SDK needs no receiver and would be enough to show interoperable output on a terminal.
- **Code:** replace `tracing.span` with the API's `tracer.start_as_current_span`, keep the existing context and `traceparent` handling (the API's W3C propagator makes them equal), and add the exporter configuration; the `connector.call`, `http.request`, `outbox.submission` and `ingestion.job` span names and attributes carry over unchanged.
- **Grafana:** a running Grafana with a Prometheus data source would be needed to demonstrate the dashboard; both are container images of a few hundred megabytes. Until then the dashboard is valid JSON checked against the recorded metrics and has never been rendered.
Approval needed: the two PyPI packages (small), and, only if a live demonstration is wanted, the collector or backend images and Grafana/Prometheus images. Until then V41-22.02 stays Partial.
